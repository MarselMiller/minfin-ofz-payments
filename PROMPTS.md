# Как решить задачу сбора данных с сайта через промпты: выплаты по ОФЗ с сайта Минфина

**Задача:** собрать с сайта Минфина все купонные выплаты и погашения ОФЗ за 2024-2026 годы в одну таблицу «дата, номер выпуска, тип платежа, сумма».

**Результат:** три независимых метода сбора (скрытое API сайта, разбор HTML, браузер) дали одинаковую таблицу: 449 строк по 140 сообщениям и 78 выпускам, «Итого» сошлось в каждом сообщении. Тетради с ячейкой периода запускаются локально в VS Code на Windows. Агент собирает любой период по сообщению в чате теми же тремя методами и выдает файл, только если все три совпали.

Ниже промпты в порядке работы. После каждого коротко: что вернул ассистент и что решил я.

## Подготовка среды

- Нужен ИИ-ассистент, который выполняет код в репозитории: читает и пишет файлы, запускает Python и git. Я работал в Claude Code с подключенным репозиторием GitHub.
- Ассистенту нужен сетевой доступ к сайту-источнику. В моей среде сеть по умолчанию закрыта, и домен minfin.gov.ru пришлось добавить в разрешенные в настройках окружения. Без этого ассистент не видит сайт, и работа уходит в обходные схемы.
- Ключ API не нужен: агент для произвольного периода работает через того же ассистента в чате.
- Для локального запуска: Python 3.11 или новее, VS Code с расширениями Python и Jupyter, окружение `.venv` с библиотеками из `requirements.txt`. Браузер для Playwright тетрадь скачивает сама.

## Промпты

### 1. Задача и устройство работы

> С сайта Минфина https://minfin.gov.ru/ru/perfomance/public_debt/internal/operations/payments/info_payment/ мне нужно достать данные о выплатах по ОФЗ за 2024-2026 годы: дата выплаты, номер выпуска, тип платежа (купон или погашение) и сумма. Нужны только фактические выплаты, без плановых графиков.
>
> Хочу сделать это тремя методами: через API, парсингом HTML и через браузер. Что именно стоит за каждым методом, обсудим по ходу, когда станет понятно, как устроен сайт.
>
> Сначала договоримся о структуре работы. Порядок:
> 1) ты быстрыми тестовыми запросами проверяешь гипотезы, как можно достать данные;
> 2) опрашиваешь меня о том, что неясно;
> 3) выносишь решения списком вариантов с рекомендацией, я отвечаю кодами;
> 4) реализуешь только утвержденное.
>
> Работаем по шагам, к следующему переходим после моего одобрения.
>
> Правила:
> - до утверждения только небольшие тестовые запросы, и перед ними пиши, что и зачем проверяешь;
> - любой тяжелый запуск только после оценки времени и числа запросов и моего слова ЗАПУСК;
> - сторонние источники данных только после отдельного обсуждения;
> - если не хватает информации, спрашивай, не додумывай;
> - делай просто и быстро: без лишней инфраструктуры, общих модулей и параллельных агентов, если они не ускоряют дело;
> - отвечай тезисно.
>
> Результат: три папки, по одной на метод. В каждой одна тетрадь ipynb (сбор, преобразование, проверки), краткий отчет и датасет, полученный этим методом. Первая ячейка каждой тетради это период по дате выплаты, который я вписываю руками. Каждая тетрадь собирает данные сама от начала до конца, и результаты трех методов должны совпасть строка в строку. Отдельно тетрадь сверки. Проверки предложи сам: они должны показать, что ничего не потеряно и не задвоено. Сейчас код выполняешь у себя, доступ к сайту в окружении открыт, работаем в ветке minfin. Но в итоге тетради должны запускаться и у меня локально, в VS Code на Windows.

- **Ассистент:** проверил готовые источники и доступ к сайту. Официального API у Минфина нет, архив Банка России заканчивается 2012 годом, API Московской биржи дает купон на одну облигацию, а не сумму по выпуску. Сайт отвечает 503 «Доступ временно ограничен» на подпись библиотеки requests и даже на честную подпись с названием проекта, а пропускает только подпись браузера. Файл robots.txt разделы с сообщениями не запрещает.
- **Я:** сторонние источники не берем, источник один, сайт Минфина. Запросы идут с подписью браузера и паузой между ними.

### 2. Устройство сайта и три метода

> Сайт устроен так (три скриншота):
> 1) лента карточек, по одной на сообщение о выплате, в каждой ссылка на docx;
> 2) в docx таблица: номер выпуска, номер купона, ставка, купонный доход, сумма; есть разделы «Выплаты купонного дохода» и «Погашение» и строка «Итого перечислено из бюджета»;
> 3) у каждого сообщения своя страница с той же таблицей в HTML.
>
> Официального API нет, готовые источники не подходят. Но лента подгружается кнопкой «Посмотреть еще» без перезагрузки страницы, значит, сайт сам запрашивает данные у сервера. Эти внутренние запросы и есть скрытое API. Отсюда три метода:
> 1) скрытое API: найди запрос, которым сайт подгружает ленту, получи по нему список сообщений и забери таблицы из docx;
> 2) парсинг HTML: обходим ленту и страницы сообщений обычными запросами и разбираем таблицы из HTML;
> 3) браузер: те же страницы через настоящий браузер, на случай если сайт отдает данные только после выполнения JavaScript или защищается от простых запросов.
>
> Решения по данным:
> - погашение это отдельный тип платежа;
> - тип платежа определяем по разделу таблицы; если встретится раздел, которого мы не знаем, разбор останавливается и ты выносишь его мне;
> - как минимум сумма строк каждого сообщения должна сходиться с «Итого», а ключ «дата + выпуск + тип» не должен повторяться.
>
> Перед полным сбором дай список оставшихся решений и оценку времени по каждому методу.

- **Ассистент:** нашел внутренний адрес ленты. Он отвечает только на запрос с заголовком X-Requested-With, как от самой страницы, а фильтр по дате публикации работает прямо в адресе. Встроенный поиск сайта отдает JSON, но не больше 4 документов за раз, для сбора он не годится. Вынес решения списком:
  - период считаем по дате выплаты из заголовка сообщения, а ленту фильтруем по дате публикации с запасом;
  - колонку «вид ОФЗ» не делаем: по номеру серий 36xxx и 39xxx его не определить;
  - оценка: 4-9 минут на метод, три метода запускаются параллельно.
- **Я:** принял рекомендации и написал ЗАПУСК.

### 3. После первого прогона: типы платежей и чистовой вид

> Раздел «Выплата» в единственном числе это тот же купон, учти его как купон. Частичное погашение сделай третьим типом платежа: это не купон и не полное погашение, смешивать их нельзя. Перезапусти сбор тремя методами, ЗАПУСК.
>
> Потом приведи ветку в чистовой вид: оставь только то, что нужно для результата и его воспроизведения. Предложи варианты, что оставить и как разложить по папкам, я выберу.

- **Ассистент:** после перезапуска три метода совпали строка в строку. Получилось 449 строк по 140 сообщениям и 78 выпускам: 425 купонов, 18 погашений и 6 частичных погашений. «Итого» сошлось во всех сообщениях. Сбор занял 3,7 минуты через API, 4,4 минуты через HTML и 7-9 минут через браузер. Варианты чистового вида:
  - убрать остатки разведки;
  - сохранить скачанные страницы, чтобы все воспроизводилось без сайта;
  - вынести сверку в отдельную папку;
  - итоговый CSV записывать только при полном совпадении методов.
- **Я:** выбрал варианты кодами одной строкой.

### 4. Агент для любого периода

> Хочу агента, который по моему сообщению в чате собирает эти же данные за любой период всеми тремя методами, сверяет их и выдает итоговый файл, только если все три совпали. Ключа API нет.
>
> Как он работает:
> - код не дублирует, а выполняет уже проверенные тетради трех методов и сверки, подставляя период вместо первой ячейки;
> - итоговый CSV и короткий отчет кладет в отдельную папку `data_files` в корне, папка `agent` служебная;
> - промежуточные файлы методов хранит в служебной папке вне git: после успешной сверки они удаляются, при проблеме остаются, пока мы ее не решим;
> - методы работают независимо: если один упал, два других все равно прогоняются, а в ответе виден статус каждого, чтобы было понятно, сколько методов и что именно чинить.
>
> Правила агента:
> - если я не дал нужную информацию (например, точные даты), спрашивает и ничего не додумывает;
> - перед любым обращением к сайту оценка времени и мое разрешение словом ЗАПУСК;
> - техническую поломку чинит сам; смысловую проблему (новый раздел таблицы, не сходится «Итого», методы разошлись) выносит мне;
> - папка универсальная: агента можно запустить в чате с любым ИИ, который умеет выполнять код.
>
> Ответ агента в чате: три абзаца «Итог», «Что произошло», «Что дальше», связным текстом, без маркированных списков. Методы называть HTML, скрытое API, браузер, технические подробности писать прямо в тексте. Если нужно мое решение, в последнем абзаце нумерованные варианты с рекомендацией.
>
> Сначала обсуди со мной, что будет в папке `agent` и как агент будет со мной взаимодействовать. Потом покажи симуляцию, не запуская по-настоящему: пустой чат, я пишу «запусти агента по сбору данных с сайта Минфина». Найдешь недочеты, предложи исправления. Сборку начинай только после моего слова СОГЛАСЕН.

- **Ассистент:** развел три варианта, что считать агентом: программу без ИИ, ИИ с нашим кодом и ИИ, который сам читает HTML. Предложил состав папки. В симуляции нашел два недочета: после технической починки агенту пришлось бы снова идти на сайт, а в новом чате ИИ мог не найти инструкцию.
- **Я:** выбрал ИИ с нашим кодом и утвердил оба исправления: пересборку из сохраненных страниц без сайта и файл AGENTS.md в корне, который направляет любой ИИ к инструкции агента. Написал СОГЛАСЕН.
- **Ассистент:** собрал агента. В него вошли инструкция для ИИ, запускатель, который выполняет ячейки тетрадей с подставленным периодом и печатает статус каждого метода, и тесты разбора на сохраненных страницах без обращения к сайту. Ответ сайта 503 останавливает сбор целиком, чтобы не ходить на сайт после отказа.
